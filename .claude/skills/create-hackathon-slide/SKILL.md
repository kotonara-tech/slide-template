# ことテク2026 ハッカソン チーム発表スライド生成

チームの成果物（リポジトリ）を読み、`hackathon-2026/team-slide-template.md` の
プレースホルダーを埋めて、ことなら（kotonara.tech）ブランドの発表用 PPTX までビルドする。

発表フォーマットは **発表8分＋デモ2分＋質疑応答3分程度・9枚固定**。
このスキルの仕事は「チームがコードに費やした2日間を、審査項目に効く13分のストーリーに
翻訳する」ことであって、スライドの体裁づくりではない。体裁はテンプレートとビルドスクリプトが
全部やるので、あなたは中身（事実の抽出と構成）に集中する。

## 0. 正となるファイルを先に読む

構成・時間配分・md 文法の正は、このスキル本文ではなくリポジトリ側にある。
毎回、次の2つを読んでから作業を始める（改訂されている可能性があるため）:

- `hackathon-2026/README.md` — 9枚構成と時間割、審査項目5つとスライドの対応、
  「md を編集するときの約束ごと」の節（ビルドが落ちる書き方の一覧）
- `hackathon-2026/team-slide-template.md` — テンプレート本体。各スライドの
  `<!-- note: ... -->` は発表者向けの台本ガイドで、何を書くべき欄なのかの説明を兼ねる

リポジトリルート（`hackathon-2026/` がある場所）以外で起動された場合は、まず
slide-template リポジトリの場所を確認してから進める。

## 1. 成果物の場所を確認する

引数はチーム成果物の場所（ローカルパスまたは git URL）。

- ローカルパス → そのまま読む
- git URL → `hackathon-2026/output/` 配下に clone する（output/ は .gitignore 済みなので
  テンプレートリポジトリを汚さない）
- 引数なし → 何を読めばよいかユーザーに聞く。推測で近くのディレクトリを漁らない

## 2. 生成は Sonnet のサブエージェントに実行させる

以降の生成作業（手順3〜6: 深く読む → 埋める → ビルド検証）は、Agent ツールで
subagent_type "general-purpose"・model "sonnet" のサブエージェントを起動して実行させる。
成果物リポジトリの精読と約60箇所の穴埋めはトークンを大量に消費する作業で、
高価なモデルの本体セッションでやる理由がない。本体は検収とチームとのやり取りに徹する。

サブエージェントのプロンプトに含めるもの:

- チーム成果物の場所と、slide-template リポジトリのルートパス
- 「このスキル（.claude/skills/create-hackathon-slide/SKILL.md）の手順3〜6を実行せよ。
  作業をさらに別のエージェントへ委譲してはならない」という指示
- 出力先: hackathon-2026/output/<チーム名スラッグ>-slides.md
- リポジトリ内で書き込んでよいのは hackathon-2026/output/ のみ・git 操作禁止という制約
- 返答してほしいもの: 生成物のパス、各スライドに書いた内容の要約、
  チームに確認が必要な質問の一覧

サブエージェントが戻ったら本体で行うこと:

- ビルドをもう一度実行して ALL OK を自分の目で確認する（数秒で終わる検収）
- 質問一覧をユーザー（チーム）に確認し、回答を md の {{...}} に反映して再ビルドする。
  この穴埋めは軽作業なので本体が直接やってよい

Agent ツールが使えない環境では、この体制はあきらめて本体がそのまま手順3〜6を実行する
（体制より成果物を優先する）。

## 3. 成果物を深く読む

README だけで書いたスライドはすぐ見抜かれる。次を読んで、発表に使える「事実」を集める:

- README・ドキュメント・企画メモやキャンバス類・スクリーンショット
- 主要コード（エントリポイント、画面、API）とパッケージ定義（依存関係＝技術スタックの証拠）
- コミット履歴（誰が何を作ったか、どんな順で進んだか、詰まって戻した形跡）

抽出する情報: プロダクト名／誰のどんな課題か／解決アイデア／デモで見せる操作の流れ／
技術スタックと選定理由／技術的な難所と突破の仕方／メンバーと役割分担／
運用の担い手と回し方／今後の展望／リポジトリ URL・公開 URL。

## 4. テンプレートをコピーして埋める

`hackathon-2026/team-slide-template.md` を
`hackathon-2026/output/<チーム名スラッグ>-slides.md` にコピーし、`{{...}}` を埋める。

- 9枚の枚数・並び・タイトル・表の位置（5枚目・7枚目）は変えない。時間配分が
  この構成に合わせて設計されており、審査項目5つもこの並びでカバーされる
- 表のデータ行は2〜4行の範囲で増減してよい（メンバー数・技術数に合わせる）
- スピーカーノートはそのチーム向けの台本に書き換えてよい。ただしノート先頭の
  【時間】タグと合計（発表8分＋デモ2分＋質疑3分）は守る — 当日の進行がこの前提で組まれている
- README の「md を編集するときの約束ごと」に必ず従う（`---` の扱い、`**` 禁止など。
  違反するとビルドが落ちるか、書いた内容が PPTX に出てこない）

## 5. 読み取れない事実は創作しない

メンバーの名前・役割分担・課題の当事者・運用の担い手は、成果物から読み取れないことが多い。
**分からないものを尤もらしく創作してはいけない。** 架空の人名や役割が投影される事故は
登壇者への実害になる。分からない項目はユーザー（チーム）に質問し、答えが得られるまで
`{{...}}` のまま残す — 残っていればビルドが意図的に失敗する設計で、それが
「埋め忘れたまま本番で投影する」事故を防ぐ安全弁になっている。

## 6. ビルドして検証する

リポジトリルートで:

```
python hackathon-2026/scripts/build_hackathon_slide_pptx.py hackathon-2026/output/<スラッグ>-slides.md
```

- `-o` を省くと md と同じ場所に `<名前>-kotonara.pptx` が生成される
- 初回は `pip install python-pptx`
- `--template-mode` は付けない。あれはテンプレート見本を再生成する運営用フラグで、
  プレースホルダー残存チェックを殺してしまう
- 実行末尾の自動検証が **ALL OK** になるまで完了としない。残存プレースホルダーの
  エラーが出たら（スライド番号とトークンが表示される）手順5に戻る
- 検証が失敗しても、ビルドスクリプトは pptx ファイル自体を書き出している。この
  「{{...}} が画面に見えるままの pptx」は成果物として渡さず、削除しておく。
  未完成デッキが手違いで本番に投影されるのを防ぐことが、この失敗設計の目的だから

## 7. 報告する

- 生成した md / pptx のパス
- 各スライドに何を書いたかの短い一覧（チームが事実確認しやすい形で）
- 成果物から読み取れず、チームの確認が必要な項目
- 仕上げの助言: 生成物は下書きである。課題設定・運用の話・チームのエピソードは
  リポジトリからは書ききれず、そこが審査で一番見られる。PowerPoint のノート表示で
  台本を読みながら、必ず一度通しで練習するよう伝える
